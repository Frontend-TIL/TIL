# 모노레포를 왜 쓰는지 정리

이번에 프로젝트 구조를 보면서 `monorepo`라는 개념을 다시 정리해봤다.

처음에는 단순히 “여러 프로젝트를 한 레포지토리에 넣는 구조” 정도로만 이해했는데, 실제로 프로젝트 규모가 커질수록 모노레포가 단순 폴더 정리 방식이 아니라 **코드 공유, 의존성 관리, 배포 단위 분리**를 위한 구조라는 걸 느꼈다.

## 모노레포란?

모노레포는 여러 애플리케이션이나 패키지를 하나의 Git 저장소에서 함께 관리하는 방식이다.

예를 들어 하나의 서비스 안에 이런 코드들이 있을 수 있다.

```text
apps/
  web/
  admin/
  mobile/

packages/
  ui/
  config/
  utils/
  api/
```

`apps`에는 실제 실행되는 애플리케이션이 들어가고,
`packages`에는 여러 앱에서 공통으로 사용하는 코드가 들어간다.

즉, 모노레포는 단순히 프로젝트를 한 곳에 모아두는 게 아니라, **여러 앱이 공통 코드를 안정적으로 공유할 수 있게 만드는 구조**에 가깝다.

---

## 왜 모노레포를 사용할까?

가장 큰 이유는 **공통 코드 관리**다.

서비스가 커지면 비슷한 코드가 여러 곳에서 반복된다.

예를 들면 버튼, 모달, API 타입, ESLint 설정, Tailwind 설정, 날짜 포맷 함수 같은 것들이다.
이걸 각각의 레포지토리에서 따로 관리하면 수정할 때마다 여러 프로젝트를 동시에 고쳐야 한다.

모노레포에서는 이런 공통 코드를 `packages/ui`, `packages/utils`, `packages/config` 같은 형태로 분리해두고 여러 앱에서 가져다 쓸 수 있다.

```ts
import { Button } from "@repo/ui";
import { formatDate } from "@repo/utils";
```

이렇게 되면 공통 UI나 유틸이 변경됐을 때 한 곳에서 관리할 수 있고, 각 앱은 같은 기준을 공유할 수 있다.

---

## 모노레포의 장점

### 1. 공통 코드 재사용이 쉽다

여러 앱에서 같은 UI, 타입, 설정을 공유할 수 있다.

예를 들어 사용자 앱과 관리자 앱이 둘 다 같은 디자인 시스템을 사용한다면, 버튼이나 입력 컴포넌트를 각각 만들 필요가 없다.

```text
apps/web
apps/admin
packages/ui
```

`web`과 `admin`이 모두 `packages/ui`를 바라보게 만들면 된다.

이렇게 하면 디자인이나 동작이 바뀌었을 때 한 번만 수정해도 여러 앱에 반영할 수 있다.

---

### 2. 설정을 통일하기 좋다

프로젝트가 여러 개로 나뉘면 ESLint, Prettier, TypeScript, Tailwind 설정이 조금씩 달라지기 쉽다.

처음에는 별 차이가 없어 보여도, 시간이 지나면 프로젝트마다 코드 스타일이나 빌드 설정이 달라지고 유지보수가 어려워진다.

모노레포에서는 공통 설정을 패키지로 빼서 관리할 수 있다.

```text
packages/eslint-config
packages/typescript-config
```

이렇게 해두면 각 앱은 공통 설정을 가져다 쓰기만 하면 된다.

---

### 3. 변경사항을 한 번에 추적하기 쉽다

예를 들어 API 타입이 바뀌었고, 그 타입을 사용하는 web, admin, mobile 앱도 같이 수정해야 한다고 하자.

멀티레포라면 각 레포지토리를 따로 수정하고 PR도 따로 올려야 한다.
하지만 모노레포에서는 관련 변경사항을 하나의 PR로 묶을 수 있다.

이게 생각보다 크다.

프론트엔드에서 타입 하나 바뀌었을 때, 그 영향을 받는 UI나 API 호출부까지 한 번에 확인할 수 있기 때문이다.

---

### 4. 패키지 간 의존성을 명확히 볼 수 있다

모노레포를 잘 구성하면 어떤 앱이 어떤 패키지를 사용하는지 구조가 보인다.

```text
web → ui, api, utils
admin → ui, api, config
```

이런 식으로 의존성이 보이면, 공통 패키지를 수정할 때 영향 범위도 더 쉽게 파악할 수 있다.

---

## 모노레포의 단점

물론 모노레포가 무조건 좋은 건 아니다.

가장 큰 단점은 **초기 설정이 복잡하다**는 점이다.

패키지 매니저, workspace 설정, 빌드 캐시, lint 범위, tsconfig 참조 등을 제대로 잡아야 한다.

작은 프로젝트에서는 오히려 모노레포가 과할 수 있다.

예를 들어 단일 웹앱 하나만 만드는 상황이라면 굳이 `apps`, `packages` 구조를 만들 필요가 없을 수도 있다.
공통화할 코드가 많지 않은데 구조만 복잡해질 수 있기 때문이다.

---

## 모노레포에서 자주 쓰는 도구

모노레포는 보통 아래 도구들과 같이 사용된다.

```text
pnpm workspace
Turborepo
Nx
Yarn workspace
```

내가 이해한 기준으로는, `pnpm workspace`는 여러 패키지를 하나의 workspace로 묶어주는 역할을 하고,
`Turborepo`나 `Nx`는 빌드, 테스트, lint 같은 작업을 더 효율적으로 실행하게 도와주는 도구다.

예를 들어 Turborepo를 쓰면 변경된 패키지와 관련된 작업만 실행하거나, 이전 빌드 결과를 캐싱할 수 있다.

```bash
turbo build
turbo lint
turbo dev
```

프로젝트가 커질수록 모든 앱을 매번 빌드하는 건 비효율적이기 때문에 이런 캐시와 task pipeline이 중요해진다.

## 예시 구조

간단한 프론트엔드 모노레포는 이런 식으로 구성할 수 있다.

```text
my-service/
  apps/
    web/
      package.json
    admin/
      package.json

  packages/
    ui/
      package.json
    utils/
      package.json
    eslint-config/
      package.json
    typescript-config/
      package.json

  package.json
  pnpm-workspace.yaml
  turbo.json
```

`pnpm-workspace.yaml`은 workspace에 포함할 패키지를 정의한다.

```yaml
packages:
  - "apps/*"
  - "packages/*"
```

루트 `package.json`에서는 전체 프로젝트에서 실행할 명령어를 관리할 수 있다.

```json
{
  "scripts": {
    "dev": "turbo dev",
    "build": "turbo build",
    "lint": "turbo lint"
  }
}
```

이렇게 하면 루트에서 한 번에 여러 앱이나 패키지의 작업을 실행할 수 있다.

## 모노레포에서 중요한 점

모노레포를 쓸 때 중요한 건 “한 레포에 다 넣자”가 아니다.

중요한 건 **어떤 코드를 공통으로 뺄지, 어떤 코드는 앱 내부에 둘지 판단하는 것**이다.

무조건 `packages`로 빼는 게 좋은 건 아니다.

예를 들어 특정 페이지에서만 쓰는 컴포넌트를 공통 패키지로 빼면 오히려 의존성이 복잡해진다.
반대로 여러 앱에서 반복되는 버튼, 모달, API 타입, 공통 설정은 패키지로 분리하는 게 좋다.

내 기준으로는 이렇게 나눌 수 있을 것 같다.

```text
공통 패키지로 빼기 좋은 것
- 디자인 시스템 컴포넌트
- 공통 유틸 함수
- API 타입
- ESLint / TypeScript 설정
- 공통 fetcher / axios client

앱 내부에 두는 게 좋은 것
- 특정 화면에서만 쓰는 컴포넌트
- 특정 서비스 도메인에 강하게 묶인 로직
- 해당 앱에서만 필요한 상태 관리
```

---

## 느낀 점

모노레포는 프로젝트가 커졌을 때 “정리된 구조”를 만들기 위한 선택지라고 생각한다.

단순히 여러 앱을 한 저장소에 넣는 게 아니라,
공통 코드와 앱 코드를 분리하고, 변경 영향 범위를 관리하고, 빌드와 테스트를 효율적으로 실행하기 위한 구조다.

다만 처음부터 무조건 모노레포를 선택하기보다는,
서비스가 여러 앱으로 나뉘거나 공통 코드가 반복되기 시작했을 때 도입하는 게 더 자연스럽다고 느꼈다.

결국 중요한 건 도구 자체가 아니라,
**코드를 어디까지 공유하고 어디서 분리할지 기준을 세우는 것**인 것 같다.
